# AGENTS.md

Guidance for AI coding agents (and humans) working on Fileship, an open-source, self-hosted file and media management platform.

Also read [MEMORY.md](MEMORY.md) (decisions, release facts and known traps), [PLAN.md](PLAN.md) (what is left before v6) and [I18N.md](I18N.md) (translations, style guides and glossaries). Update them when you learn something the hard way or finish a planned item.

## Repository

pnpm + Turborepo monorepo (`pnpm@11`, workspaces `apps/*` and `packages/*`). pnpm uses its default isolated linker, so every workspace declares the packages it imports.

| Path                     | What it is                                                                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `apps/dashboard`         | Nuxt 4 app: the UI and the Nitro API. Prisma/Postgres, socket.io, Orama search, local AI queue.                                                                          |
| `apps/updater-agent`     | Small h3 service (`src/index.ts`) that performs blue/green updates by driving `docker compose`.                                                                          |
| `apps/desktop`           | Fileship for Windows: a native host (tray, capture, overlay, recording, uploads, Harbor) with Electron windows and a Nuxt renderer on the ui layer, for Fileship 6.0+.   |
| `apps/extension`         | The browser extension (Manifest V3 for Chrome, Edge and Firefox, built with WXT and Vue): uploads, screenshots and short links with an upload token.                     |
| `apps/telemetry`         | Nuxt 4 telemetry panel: receives the anonymous reports and shows the statistics. Admin only. Not part of the user-facing stack.                                          |
| `packages/ui`            | `@fileship/ui`, the shared Nuxt layer: shadcn-vue components, theme tokens, generic app components and the shared Nuxt modules.                                          |
| `packages/telemetry`     | `@fileship/telemetry`, the report schema (zod) and the client that collects runtime info and sends reports.                                                              |
| `packages/ai`            | `@fileship/ai`, the AI models (SigLIP, Florence-2, text embeddings, PaddleOCR, privacy filter) running on a worker thread.                                               |
| `packages/pdf`           | `@fileship/pdf`, first-page previews of PDFs with PDFium (WebAssembly) running on a worker thread.                                                                       |
| `packages/eslint-config` | `@fileship/eslint-config`: `.` for plain TypeScript packages, `./nuxt` for the rules the Nuxt apps and the ui layer pass to `withNuxt`, `./i18n` for the vue-i18n rules. |

## Commands

Run from the repository root unless noted.

- `pnpm install`: install everything (pnpm only, enforced by `preinstall`).
- `pnpm dev`: run the dashboard in dev mode through Turbo. It generates the Prisma client and applies migrations first. The telemetry panel needs its own `.env` and runs with `pnpm --filter telemetry dev`.
- `pnpm build`: build every workspace.
- `pnpm lint`: `lint:i18n` (`scripts/check-i18n.mjs`: `en` and `tr` catalogs have the same keys and every message compiles), ESLint in every workspace, then `prettier --write .`.
- `pnpm lint:types`: `nuxt typecheck` in the dashboard, the telemetry panel and the ui layer, `nuxt typecheck` and `tsc` for the main process in the desktop app, and `vue-tsc` in the browser extension. It must report zero errors.
- `pnpm check`: build + lint + lint:types, which is what CI runs (`.github/workflows/check.yml`, on Linux, where the desktop build skips the native addon and the Harbor helper).

Dashboard only (`pnpm --filter dashboard <script>`):

- `lint:code`: `eslint --fix .`
- `db:generate`, `db:deploy`, `db:migrate` (create-only), `db:prototype` (db push), `db:studio`, `db:reset`.

Desktop app only (`pnpm --filter desktop <script>`): `dev` (builds the host and the Harbor helper, starts Nuxt on port 3020, the host on a dev pipe and Electron, and restarts Electron on main process changes) and `package` (builds `release/Fileship-Setup-<version>.exe` locally).

Telemetry panel only (`pnpm --filter telemetry <script>`): `dev` (port 3002), `db:generate`, `db:deploy`, `db:migrate` (create-only) and `db:studio`.

Browser extension only (`pnpm --filter extension <script>`): `dev` and `dev:firefox` (WXT starts a browser with the extension and reloads it), `build` (`.output/chrome-mv3` and `.output/firefox-mv3`), `package` (the store zips and the sources zip for addons.mozilla.org) and `test` (vitest for the API and upload client).

Turborepo behaviour can differ between versions. Before changing `turbo.json`, read the docs bundled with the installed package (`node_modules/turbo/docs`).

## Environment

- `apps/dashboard/.env.example` lists every dashboard variable. Only `DATABASE_URL` is required. Optional groups: storage (`NUXT_DATA_DIRECTORY`), site (`NUXT_PUBLIC_SITE_NAME`, `NUXT_PUBLIC_RETURN_HTTPS`), updater (`NUXT_UPDATER_URL`, `NUXT_UPDATER_SECRET`), trash (`NUXT_TRASH_RETENTION_DAYS`), scheduled backups (`NUXT_SCHEDULED_BACKUPS_ENABLED`), logs (`NUXT_LOG_LEVEL`), crons (`DELETE_EXPIRED_CRON`, `GENERATE_STATS_CRON`), uploads (`NUXT_PUBLIC_FILE_CHUNK_SIZE`, `NUXT_REMOVE_EXIF_DATA`, `NUXT_AVATAR_MAX_SIZE`), Turnstile, email (`NUXT_SITE_URL`, `NUXT_SMTP_*`), PWA (`ENABLE_PWA`), telemetry and the `NUXT_AI_*` / `NUXT_PUBLIC_AI_ENABLED` group.
- Self-registration is off by default. `NUXT_PUBLIC_REGISTRATION_ENABLED=true` enables `/register` and `POST /api/auth/register` (an invite link, `/register?invite=`, works either way); `NUXT_REGISTRATION_PERMISSIONS` (only `UploadFiles`, `TakeNotes` and `ShortenLinks` are honoured) and `NUXT_REGISTRATION_USABLE_SPACE` (MB, `-1` unlimited) set what new accounts get.
- Single sign-on: `NUXT_OIDC_ENABLED`, `NUXT_OIDC_ISSUER_URL`, `NUXT_OIDC_CLIENT_ID`, `NUXT_OIDC_CLIENT_SECRET`, `NUXT_OIDC_BUTTON_LABEL` and `NUXT_OIDC_AUTO_REGISTER` (accounts for unknown people, with the registration permissions and usable space) are the defaults of the `oidc*` settings, and `NUXT_PASSWORD_LOGIN_ENABLED` of `passwordLoginEnabled`. Single sign-on needs the `siteUrl` setting too.
- `NUXT_UPDATER_URL` and `NUXT_UPDATER_SECRET` point the dashboard at the updater-agent. `docker-compose.yml` sets both.
- The updater-agent reads `PORT`, `SECRET_TOKEN`, `DEV_MODE`, `AUTOUPDATER_ENABLED`, `AUTOUPDATER_CRON`, `COMPOSE_FILE` and `FILESHIP_URL`.
- `NUXT_TELEMETRY_URL` sends the dashboard's reports to another panel. Development builds only send reports when it is set.
- The telemetry panel (`apps/telemetry/.env.example`) reads `DATABASE_URL`, `NUXT_ADMIN_PASSWORD` (the panel stays locked while it is empty) and `NUXT_INSTANCE_RETENTION_DAYS`.
- Instance settings (site name, dashboard address, link protocol, uploads, trash retention, scheduled backups, registration, single sign-on, Turnstile, AI, log level, telemetry, email, webhook private targets, active storage) are stored in the `Setting` table and edited by super admins at `/dashboard/instance`. The env/runtimeConfig values are only their defaults. Server code reads them with `getSettings()` (or `getSettingsSync()` in synchronous code) from `server/utils/settings.ts`; the client reads the public subset with `usePublicSettings()`, kept in sync over the `settings:update` socket event. The schema lives in `shared/utils/settings.ts`. `GET /api/settings` blanks the `secretSettingKeys` and sends `secretsSet` flags instead, and `smtpPassword` and `oidcClientSecret` are stored AES-GCM encrypted (`encryptedSettingKeys`).
- Server code reads the remaining configuration through `useRuntimeConfig()`, never `process.env`. Runtime overrides therefore use the `NUXT_` prefix. The exceptions are `DATABASE_URL` (shared with the Prisma CLI) and the build-time options in `nuxt.config.ts` (`ENABLE_PWA`, `DELETE_EXPIRED_CRON`, `GENERATE_STATS_CRON`), which only take effect when the app is built.
- Never commit `.env` files, `data/` or anything under `.claude/` or `.impeccable/`.

## Translations

The dashboard, the desktop app and the browser extension are translated into English (source and fallback), Turkish, German, Spanish, French, Italian, Brazilian Portuguese, Russian, Azerbaijani, Japanese, Korean and Simplified Chinese; the telemetry panel is English only. [I18N.md](I18N.md) has the catalog layout, the code rules, the style guides and the glossaries.

- Every user-visible string is a key, in both `en` and `tr`. ESLint rejects raw template text and unknown keys, and `pnpm lint:i18n` rejects catalogs that differ.
- The ui layer registers `@nuxtjs/i18n` (`no_prefix`, so URLs never change) with its own `common` and `error` messages in `packages/ui/i18n`. Each app adds its locales from `i18n/locales/<code>.json` (`en`, `tr`, `de`, `es`, `fr`, `it`, `pt`, `ru`, `az`, `ja`, `ko`, `zh`; the list is `LANGUAGES` in `apps/dashboard/shared/utils/languages.ts` and `apps/desktop/i18n/messages.ts`): the dashboard loads them as locale files, the desktop app bundles them through `i18n/messages.ts`.
- A code names a language, not a region: `es` is one neutral Spanish, `pt` is Brazilian Portuguese and `zh` Simplified Chinese, and every browser or Windows language resolves by its first part (`es-419` → `es`, `pt-PT` → `pt`). Plural forms are picked by `pluralIndex` (`packages/ui/i18n/plural.ts`: French counts 0 as singular, Russian has one, few and many forms), which every translator uses (vue-i18n `pluralRules`, emails, webhook messages, the Electron main process, the extension); the host's `choose` in `native/shared/i18n.cpp` mirrors it.
- Dashboard: the language is `User.language` (`null` follows the browser), changed on the appearance page (`updateLanguage`), applied during SSR in `fetchCurrentUser` and synced over `currentUser:update`; guests use the `fileship_locale` cookie or `Accept-Language`. `i18n/localeDetector.ts` resolves the same order on the server, `server/middleware/0.i18n.ts` stores `event.context.t` (refreshed in `auth.ts` once the user is known), and API errors are thrown with `apiError(status, key)` / `invalidBodyError(error)` from `server/utils/i18n.ts`. Clients never compare error messages; the API adds flags to `data` instead. Logs stay English.
- Dates use `useDate()` (dayjs with the active locale and localized formats; `plugins/dayjs.ts` registers dayjs's `pt-br` locale as `pt`), numbers `Intl` with the active locale.
- Desktop: the `language` setting (`system` follows Windows) is resolved by the host, whose `t()` (`native/shared/i18n.h`, catalogs merged into `build/host/i18n`) translates the tray, notifications, the overlay and dialogs; a change refreshes the tray and broadcasts `app:language` to Electron (`electron/i18n.ts`) and every window (`app/plugins/language.client.ts`). API requests send `Accept-Language`, so server errors arrive translated.
- Browser extension: there is no language setting; `t()` in `utils/i18n.ts` follows the browser's UI language (`i18n.getUILanguage()`) and is also the `$t` of its Vue pages. Its catalogs (`apps/extension/i18n/locales`) are merged with the ui layer's in `i18n/messages.ts`, and the build writes `manifest.description` to `_locales/<folder>/messages.json` for the manifest (`pt_BR` and `zh_CN` for `pt` and `zh`; Chrome gets no `az`). API requests send `Accept-Language`.

## Deployment model

`docker-compose.yml` runs `postgres`, a Caddy `proxy` (`caddy.json`), `fileship-blue`, `fileship-green` (profile `green`) and `updater-agent`.

- Caddy uses the `first` selection policy with active health checks on `/api/healthz`, so traffic goes to the first healthy color.
- An update pulls the image for the idle color, starts it, waits for `ready: true`, and then stops the old color. If the new color exits, dies or never becomes healthy, the agent stops it again and the old color keeps serving.
- `/api/healthz` returns `{ status, version, ready, busy }`. `busy` is true while any backup restore is running; the agent waits for it (up to 10 minutes) before stopping the old color, and the auto-updater skips a run when busy.
- Both colors share the database and `data/`. Startup and scheduled work must be idempotent and safe to run twice (for example, `resetBackupRestoreState` only clears restores older than 2 hours, `storage:sync` skips a storage that cannot be listed or looks empty, and `backups:run` claims each due schedule with a compare-and-swap on `nextRunAt`).
- `docker-compose.dev.yml` is the same stack built from local Dockerfiles, with development settings (no container health checks, the updater on port 3001 in dev mode, no auto-updates).
- Images (`apps/<app>/Dockerfile`, published by `docker-publish.yml` for `linux/amd64` and `linux/arm64`): the builders run on the build platform (`FROM --platform=$BUILDPLATFORM`), never under QEMU, and cross-build for the target. They install only the app and its workspace packages, for the build CPU and the target CPU (`--filter <app>... --os=current --libc=current --cpu=current --cpu=<target>`). `scripts/retarget-natives.mjs` then makes the output native for the target: it swaps the build CPU's platform packages (ffmpeg, ffprobe, sharp, canvas) for the target's, keeps only the target's node-gyp prebuilds and onnxruntime binaries, and fails the build if any ELF file is for another CPU. The Prisma CLI's schema engine is downloaded for the target with `PRISMA_CLI_BINARY_TARGETS`. Only the runner's `apt-get` runs under emulation. The dashboard and telemetry runners ship the Nitro `.output` (its `node_modules` is all the server loads, including the AI and PDF workers' dependencies and the ffmpeg, sharp, canvas and onnxruntime binaries), `prisma/` and the Prisma CLI that `prisma migrate deploy` runs at start, traced by `scripts/prisma-cli.mjs` with `@prisma/engines`. Nothing else from the workspace is in the image, so a file the server loads by path at runtime must be traced (`traceInclude`) or copied into `.output` (the `compiled` hook). The updater-agent runner ships the agent with only its production dependencies (`pnpm deploy --prod --legacy`) and runs it with `node .`.

## Shared UI layer (`packages/ui`)

- A Nuxt layer shipped as source. The dashboard and the telemetry panel use it through `extends: ['@fileship/ui']`, and its `components`, `composables`, `utils`, `layouts` and `plugins` are auto-imported there. The browser extension uses its components, theme tokens and catalogs without Nuxt (see [Browser extension](#browser-extension-appsextension)), so keep the shadcn-vue components free of Nuxt-only APIs.
- `app/components/ui`: shadcn-vue components (style `reka-luma`, see `packages/ui/components.json`). Run `shadcn-vue add` from `packages/ui`.
- Generic components: `AppHeader` (sidebar trigger, breadcrumbs, theme toggle), `PageHeader`, `TextBlock`, `EmptyState`, `Centered`, `StatCard`, `StatsDonut`, `TrendChart`, `DataTable`, `VirtualList`, `ListCardSkeleton`, `PasswordInput`, `ConfirmDialog` and `AppToaster` (the Sonner toaster every app renders: `rounded-3xl` toasts with `buttonVariants` action and cancel buttons; `tailwind.css` releases vue-sonner's unlayered radius and button styles with `revert-layer` so those classes apply). Composables: `useConfirm`, `useQueryState`, `useBreadcrumbs`, `useBreadcrumbLabels`, `useBreadcrumbTrail` (extra crumbs inserted before the last one while `path` matches the route, used for folder ancestors). Utils: `cn`, `pluralize`, `clamp`, `getErrorMessage`.
- `app/error.vue` is the error page of every app. Its home button leads to the `home` app config (`{ path, label }`), which each app sets in its own `app/app.config.ts`.
- `app/styles/tailwind.css` holds the Fileship theme tokens (light and dark). Each app imports it from its own `app/styles/tailwind.css` (`@import '@fileship/ui/app/styles/tailwind.css';`). The tokens set `color-scheme`, and the layer's `color-scheme` plugin writes the matching `<meta name="color-scheme">` from the color-mode preference (on the server from the cookie), so a browser paints the right canvas before the stylesheets load. Its `theme-color` plugin does the same for `<meta name="theme-color">` with the `--background` colors (`#ffffff` / `#0a0a0a`), never an accent, so the mobile browser bar matches the page; it always writes a light and a dark tag with `media`, and only their content follows the preference. The dashboard adds its accent colors after it; the panel uses only the default colors.
- Inside the layer, `@/` and `~/` point to the app that extends it. Import layer files through `#layers/ui/...` instead, for example `#layers/ui/app/components/ui/sidebar`.
- The layer declares every module and package it uses (`@nuxt/fonts`, `@nuxtjs/color-mode`, `@vueuse/nuxt`, `vue-sonner/nuxt`, `nuxt-lucide-icons`, `@nuxt/eslint`, Tailwind, reka-ui, Unovis, ...). Apps add only what they import themselves.
- Put something here only when both apps use it or it is part of the design system. Anything that needs `useAuthUser`, the socket or Fileship APIs stays in the dashboard.

## Key building blocks

Reuse these instead of writing new versions.

- `usePaginatedList(resource, endpoint, params, options)` (`app/composables/usePaginatedList.ts`): infinite list state (`items`, `total`, `summary`, `isLoading`, `isError`, `hasMore`, `loadMore`, `refresh`). Pages show an `EmptyState` with a retry (`refresh`) while `isError` is set; a failed background refresh keeps the items already shown. Socket events update every open list through `refreshLists`, `patchListItem`, `removeListItems` and `mapListItems`. `useListHandle` registers single items for detail pages.
- `DataTable.vue`: window-virtualized table. Columns support `sortable` and `descFirst`; it switches to a `#card` slot below 640px of container width and emits `reachEnd`.
- `VirtualList.vue`: window-virtualized responsive grid (`minItemWidth`, `gap`, `estimateSize`, `reachEnd`). With `contained` it virtualizes against its nearest scrolling ancestor instead (dropdowns, command lists, dialogs).
- `useQueryState(key, default)`: a ref bound to the URL query. It drops defaults and batches updates.
- `askConfirmation({ ..., action })` (`useConfirm.ts`): confirmation dialog that keeps a spinner until `action` resolves.
- `withVerification(action)` (`useVerification.ts`): retries an action after a password, TOTP or passkey prompt when the API asks for verification.
- `getErrorMessage(error)`: user-facing message from a fetch error.
- Storage: never build `data/uploads` or `data/backups` paths. Upload and backup bytes live on a storage (`File.storageId` / `Backup.storageId`, `null` is the data directory) under the keys `uploadKey(fileName)` (`uploads/<name>`) and `backupKey(backup)` (`backups/<userId>/<id>.tgz`). Use `getStorage(storageId)` for `read`, `put`, `move`, `remove` and `list`, and `withLocalFile(storageId, key, fn)` when a tool needs a real path (sharp, ffmpeg, AI, tar). `removeFileData(files)` removes a file's bytes, thumbnail and search entry.
- Chunked uploads go through `receiveUpload` (files, inbox) or `receiveChunk` (backups) in `server/utils/upload.ts`. Chunks are written straight to the active storage, except images that need EXIF removal or compression, which are assembled in `data/temp` first. Upload sessions live in `data/temp/<owner>/<uploadId>.upload.json` and `dir:clearTemp` aborts stale ones. Chunks may arrive in any order and in parallel: the session is read and written under a per-upload lock, the bytes are written outside it at `(part - 1) * chunkSize`, every chunk must match that layout, and the upload completes when all `totalChunks` parts have arrived. A storage driver returns per-part data from `writeChunk` (S3 ETags), which `completeUpload` receives. FTP appends and is marked `isSequential`, so `/api/settings/public` sends `uploadConcurrency: 1` for it and 4 otherwise.
- Folder tree: `Folder.parentId` nests folders up to `MAX_FOLDER_DEPTH` (10, `shared/utils/constants.ts`) levels; deleting a parent row sets its children's `parentId` to null. `server/utils/folderTree.ts` has `folderAncestors(id)` (root first), `folderSubtree(ids)` (the folders plus the children that share their `deletedAt`, so the live tree or what was trashed together) and `assertFolderParent(authorId, parentId, folderId?)` (owned, not trashed, no cycles, depth limit), which create (`POST /api/folders`) and move (`PATCH` with `parentId`) run. `GET /api/folders?parent=root` lists the top level and `GET /api/folders` every folder (Harbor, pickers, search); `GET /api/folders/[id]/folders` lists the children (owners get full folders, visitors only public children as `{ id, name, createdAt }`), and `GET /api/folders/[id]` adds `folderCount` and `ancestors`. Every folder has its own `public` flag: visitors see the public children of a public folder and only the ancestors above it up to the nearest private one, and the recursive archive (`<folder path>/<fileName>`) follows the same rule. `folder:update` carries `parentId` only when the folder moved, and a deleted tree sends `folder:delete` for every folder in it. Backups export folders parents first and restore `parentId` from folders already restored.
- Team folders: a folder owner shares a folder with other users through `FolderMember` rows (`Viewer` or `Editor`; `GET` and `PUT /api/folders/[id]/members`, `DELETE /api/folders/[id]/members/[userId]` to remove someone or leave). A membership covers the folder and everything below it, and the strongest role on the folder's chain wins: `folderAccessOf(folder, userId)` (`server/utils/folderAccess.ts`) returns `owner`, `editor`, `viewer` or null. Everything in a shared tree belongs to its owner: files and folders an editor adds get the owner's `authorId`, count against the owner's usable space (`receiveUpload` keeps the upload session under the uploader and checks the owner's quota), use the owner's AI settings and go to the owner's trash. Viewers open, download and archive; editors also upload, create folders, rename (files: `name` only) and move things to the trash; moving, sharing, the public flag, file settings (link name, password, expiry, views, sensitive) and delete forever stay with the owner. Removing something needs editor access to the folder that holds it, so an editor cannot delete the shared folder itself. Folder routes use `findFolderWithAccess(id, userId, needed)`, file routes `fileAccessOf`, and file lists filtered by a folder `sharedFolderOf`; members are never treated as visitors (no `visitorFileWhere`, no password, views not counted) except for trashed files. `GET /api/folders?shared=true` lists the folders shared with the user; shared items never appear in the user's own lists (`GET /api/folders`, `/api/files?folder=all`) or Harbor. Responses to members carry `access` and the folder `owner`, and the dashboard hides what the role cannot do (`isOwnedItem`, `isEditableItem` in `app/utils/folderAccess.ts`). The folder page treats a folder without `access` (someone else's public folder) as `viewer`, says the role in its description and stores it in `useCurrentFolderAccess()`; on a folder the user can only view, `useUploader().isReadOnlyFolder` turns off every upload path in the layout (header button, `U`, palette action, drop zone, paste, upload sheet) and the page shows a view-only alert instead. Socket events for a shared tree go to the owner and every member on its chain (`sendToFolder`, `folderAudience`), and `folder:share` tells a user their access changed. Folder pages need `UploadFiles`, so members need it too. Memberships are not part of backups, so restoring one drops them.
- Trash: `File`, `Folder` and `Note` have `deletedAt`. Every query that lists, counts, serves or edits them must add `deletedAt: null` (use `userCountSelect` from `list.ts` for user counts); only the trash endpoints and `server/utils/trash.ts` (`deleteTrashed`, `delete*Forever`, `filesTrashedWith`) work on trashed rows. Storage quotas (`exceedsUsableSpace`) and the stats count trashed files, and the stats report the trashed size separately. Deleting a folder trashes its whole subtree with one `deletedAt`; files that are kept move to the deleted folder's parent. Restoring a folder restores what was trashed with it, and a restored folder or file whose parent is still in the trash goes to the top level. User deletes go to the trash while `trashRetentionDays > 0`, unless the delete confirmation's **Delete forever** button sends `permanent: true` to the delete routes; expiry, max views, `storage:sync`, user deletion and backup restores delete immediately. `db:purgeTrash` runs hourly.
- File names: `File.fileName` is the unique URL slug (`/u/<fileName>`, ASCII only, unique across the instance). `File.name` is the display name: the original upload name with Unicode, only Windows-invalid characters stripped, not unique. Show and sort by `name` in the UI, use it for downloads (`Content-Disposition`), and keep links on `fileName`.
- Links: `Link` rows are served by `/s/[code]` through `findActiveLink` and `countLinkClick` (`server/utils/link.ts`). Owner clicks are not counted, a link is deleted at its click limit, and expired links are removed by `db:deleteExpired`.
- Backups: `createBackup(owner, automatic)` (`server/utils/backup.ts`) writes the archive and the `Backup` row for both `POST /api/users/@me/backups` and scheduled backups, and `backupLimitOf(owner)` is the backup limit every path checks (`Infinity` for admins and -1). Scheduled backups (`server/utils/backupSchedule.ts`): one `BackupSchedule` row per user (`frequency` `Off`/`Daily`/`Weekly`, `hour`, `weekday`, IANA `timezone`, `keep`, `nextRunAt`, `lastRunAt`, `lastRunStatus`), edited with `GET`/`PUT /api/users/@me/backups/schedule`; `nextBackupRun` computes the next run in the user's time zone. `backups:run` runs every 15 minutes while the `scheduledBackupsEnabled` instance setting is on and handles one user at a time: it claims a due schedule by moving `nextRunAt` to the next run with `updateMany` on the old value (so the other color skips it), skips users with a restore in progress (they run once it ends), creates an automatic backup and then deletes the oldest automatic backups beyond `min(keep, backupLimit - manual backups)`. Manual and uploaded backups are never rotated, and a run is skipped as `LimitReached` while manual backups alone fill the limit. Runs are logged with `createLog(null, { user })` and sent as `backupSchedule:update`, which keeps `useBackupSchedule()` in sync.
- Webhooks: users manage up to `WEBHOOK_LIMIT` webhooks on the integrations page (`/api/users/@me/webhooks`, socket `webhook:create|update|delete`, state `useWebhooks()`), in the `Discord`, `Slack` or `Json` format. Routes call `emitFileUploaded`, `emitFilesDeleted`, `emitLinkCreated` and `emitNoteCreated` (`server/utils/webhooks.ts`) with the owner of the items, so uploads and deletes by members of a shared folder reach the folder owner's webhooks; `emitWebhookEvent` builds the payload lazily (only when an enabled webhook subscribes to the event), never throws and queues one `WebhookDelivery` row per webhook through `event.waitUntil`. Payloads only carry what a visitor could see: `visibility` is `public`, `locked` (password: link name only, no thumbnail) or `hidden` (sensitive, private folder, expired or awaiting AI analysis: link name only, no thumbnail); locked links have no `target` and private notes no `title`. `file.uploaded` stores only the file id and is rebuilt when it is sent, waiting up to 30 minutes for a pending AI job. `webhookRunner.ts` claims deliveries with `FOR UPDATE SKIP LOCKED` (`claimWebhookDelivery` in `webhookQueue.ts`, one in flight per webhook, lease 2 minutes, so both colors can run it), sends them with `sendWebhookRequest` (`webhookRequest.ts`: 10 s timeout, up to 3 redirects, every hop's address checked after DNS resolution against the blocked ranges unless `webhookPrivateTargets` is on), retries network errors, timeouts, `408`, `429` (honouring `Retry-After` through `Webhook.retryAt`, without using an attempt) and `5xx` after 10 s, 1 min, 5 min and 30 min, keeps the last `WEBHOOK_HISTORY` finished deliveries, and turns a webhook off (`disabledAt`, pending deliveries cancelled, `Disable Webhook` log) after `WEBHOOK_FAILURE_LIMIT` failed deliveries in a row. Discord and Slack bodies come from `formatWebhookMessage` (`webhookMessages.ts`), which translates with the `webhookMessages` catalog namespace in the owner's language (`User.language`, else the UI language the webhook was saved in); the generic body is version 1 and signed (`X-Fileship-Signature: sha256=<HMAC of timestamp.body>`), documented in `docs/webhooks.md`. Change that page when the payload changes, and only add fields to version 1.
- `storage:sync` runs on startup and removes files and backups whose bytes are missing, and indexes backup archives that have no row. It skips rows created in the last 15 minutes and archives of pending upload sessions, because the other color may still be finishing them. `storage:migrate` moves everything to the active storage.
- Storage import (super admins, `/dashboard/instance` → a storage's **Import files**) brings files Fileship has no row for into a chosen user's account: `findImportableFiles` (`server/utils/storageImport.ts`) lists the whole storage (S3, SFTP, FTP) or `data/uploads` plus the `data/import` drop folder, and skips `backups/`, dotfiles, `uploads/*.<id>.part` chunk files, `uploads/` names that have a row and anything modified in the last 15 minutes. `runStorageImport` runs in `event.waitUntil`, one file at a time: it skips files the user already has (same `name` and size) or that exceed their quota, moves the bytes to `uploads/<slug>` on the same storage before creating the row (keeping the original modified date), maps the folders of the path to nested folders (found by name and parent, created when missing, at most `MAX_FOLDER_DEPTH` levels), then runs `processMedia` and `indexCreatedFile` (`server/utils/fileData.ts`, AI queue and search, shared with uploads, the inbox and backup restores). Progress is in memory (`storageImport.progress`, socket `storage:import`), an import and a migration never run together, and the dialog explains these rules and shows the real `data/import` path. The per-file work (`importStoredFile`, `availableFileName`, `isDuplicateImport`) and the folder lookup (`createFolderResolver`) are shared with the app import.
- App import (super admins, a storage's **Import from another app**, `AppImportDialog.vue`) moves a Zipline (3.7 and 4.x server exports), XBackBone 3 (SQLite) or Chibisafe 6 (SQLite) instance into Fileship; `docs/migrating.md` says what is kept. The data file is streamed to `data/temp/app-import/<id>` (`POST /api/storages/import/apps/source`, removed when the import ends or by `dir:clearTemp`), and `readImportSource` (`server/utils/appImportSources.ts`) recognises it (SQLite header and tables through `node:sqlite`, or the export's `versions.export`, parsed with stream-json while skipping `request`, which holds Zipline's environment and secrets, and the metrics) and maps it to one `ImportSource` shape (users, folders, files, links, notes). Files are found on the storage (`listImportObjects`: `data/import` or the whole storage, without Fileship's own uploads and backups) by their path in the other app's folder as a path suffix, with the size checked when the source has one. `previewAppImport` counts what is there and suggests a target per account (same username, case-insensitive); `POST /api/storages/import/apps` creates the `new` accounts inside the request (`resolveImportOwners`: `createUser` with `passwordHash` keeps Zipline's Argon2 hashes, the upload, notes and links permissions and the old storage limit, never admin) and `runAppImport` (`server/utils/appImport.ts`) then imports, one item at a time: folders (nested up to `MAX_FOLDER_DEPTH` and always public, because the other apps serve every file by its link while Fileship hides the files of a private folder from visitors), files (old link name kept when free, original date, views as `View` rows on that date, view limit, expiry; hashed share passwords and private files get a random password, expired and used-up files are skipped), links (code kept when free, deduplicated by owner, URL and `createdAt`) and Chibisafe snippets as notes. Progress shares `storageImport.progress` with `app` and `missing` set.
- AI analysis: one job per file (`AnalyzeImage`, `AnalyzeVideo`, `AnalyzeText`, plus `DetectPII` when an override is cleared), queued with `enqueueFileAnalysis` and run by `runAIJob` (`server/utils/aiJobs.ts`) from the `aiQueueRunner` pool. A job downloads the file once, runs each step (image embedding, OCR, caption, text embedding, PII) and saves it right away, skipping steps whose data already exists, then sets `File.aiAnalyzedAt`. Queue guarantees (`server/utils/aiQueue.ts`): one active job per file and type (partial unique index), atomic claims with `FOR UPDATE SKIP LOCKED`, a lease renewed while the job runs, retry after the lease on errors, `Failed` after `AI_MAX_ATTEMPTS`, and finished jobs are deleted. `ai:syncJobs` queues files whose analysis is missing or was made with other models (`embeddingModel` / `textEmbeddingModel`); failed files wait for **Retry failed**, and `ai:cleanup` deletes failed jobs after 30 days so those files are queued again. `resetAIData()` (`POST /api/settings/ai-reset`) clears every file's AI data except owner overrides, deletes all jobs, rebuilds the search index and runs the sync.
- AI models and presets: `server/utils/aiPresets.ts` defines `low`, `medium` and `high` (instance setting `aiPreset`), each with its models, search cutoffs, OCR tier, keep-alive and video frames. Inference runs synchronously inside onnxruntime, so every model lives in `packages/ai` and runs on a worker thread; the main thread only talks to it through the `ai` facade in `server/utils/ai.ts` (`createAIClient`), which sends the active preset, `aiInferenceThreads` and `data/models` with every call. Pass file paths or buffers, never decoded images. A call that is running when the worker dies is rejected (the job retries) and the next call starts a new worker; the worker stops when Nitro closes. Nitro inlines workspace packages, so the `compiled` hook in `nuxt.config.ts` copies the worker to `.output/server/worker.mjs` and `traceInclude` brings its dependencies. Never import transformers, onnxruntime or ppu-paddle-ocr in the dashboard. Inside the worker, models load through `useAIModel` (`packages/ai/src/models.ts`), which shares one instance, retries after a failed load, unloads after the keep-alive and uses `getSessionOptions()` (ONNX memory arena off). PII rules (`findPii`) stay on the main thread; the worker only returns the privacy filter entities. OCR is `ppu-paddle-ocr` (`packages/ai/src/ocr.ts`): PP-OCRv6 detects text once and its boxes are recognised, then PP-OCRv5 script models run only when text regions were left unread. Choose models by measuring them (multilingual retrieval R@1, results returned for unrelated queries, OCR error rate, peak RSS within the preset's RAM budget), not by benchmarks alone; a new embedding model needs a new `key`, and its search cutoff must be calibrated.
- PDF previews: `processMedia` treats PDFs like media (`isAnalyzable`, `canHaveThumbnail`): `server/utils/media.ts` renders the first page into the thumbnail and stores `pages` and `format` in the metadata through `@fileship/pdf`. PDFium calls are synchronous, so they run on a worker thread (`createPdfClient`): one file at a time, read in blocks through `FPDF_LoadCustomDocument` instead of loading it into memory, killed after 60 s and stopped after 30 s idle. The `compiled` hook copies the worker to `.output/server/pdf-worker.mjs`, and `traceInclude` brings `pdfium.wasm`. In the browser, `PdfViewer` (the dashboard file viewer and the public view page) loads the pdf.js legacy build on demand (`app/utils/pdfjs.ts`), draws the visible pages on canvases in a virtualized list and fetches `/u/<fileName>` with range requests (the public page downloads the whole file, so a view limit is reached by one request). Its cmaps, fonts, ICC profiles and decoders are served from `/_pdfjs/<version>/` (`nitro.publicAssets`). Other documents (Office, ODF) have no preview, because that needs LibreOffice in the image. The dashboard file viewer remounts `PdfViewer` per file (`:key`), and `PdfViewer` calls `measure()` once a new document's pages are in the DOM; otherwise the virtualizer's size cache from the previous document keeps the pages blank until the user scrolls.
- Text previews: `textPreviewLanguage(name, mimeType)` (`shared/utils/fileTypes.ts`) decides whether a file previews as text and which highlight.js language it gets: by file name (`Dockerfile`, `Makefile`, ...), by lowercased extension (`TEXT_PREVIEW_LANGUAGES`), then by MIME (`text/*`, JSON, JavaScript, XML, YAML, TOML, shell, `+json`/`+xml`). `TextPreview` (the dashboard file viewer and the public view page) fetches `/u/<fileName>` with `responseType: 'text'`, so JSON is shown byte for byte and never parsed, skips files over `TEXT_PREVIEW_MAX_SIZE` (2 MB), renders Markdown with `MarkdownRenderer`, highlights code with highlight.js directly (up to 512 KB) and shows plain text as is. `video/mp2t` only counts as video when its metadata has a duration (`isVideoFile`), so TypeScript `.ts` files preview as code. `TEXT_FILE_TYPES` is only the upload sheet's list of new text file types. Uploads whose browser sent no MIME type get one from the file name (`uploadMimeType` in `server/utils/upload.ts`); browsers send such parts as `application/octet-stream`, so that type is looked up by name too.
- Sensitive content: `ai.detectPII` runs the OpenAI Privacy Filter over the OCR text or file text (and uses the image caption to recognize photos of cards and ID documents), and `findPii` (`server/utils/pii.ts`) turns its spans into reasons and adds the structural validators (Luhn with card network prefixes, IBAN mod 97, ICAO MRZ check digits). Keep it free of country-specific rules. Reason codes and their labels are in `shared/utils/pii.ts`. `PERSON_NAME` and `PRIVATE_DATE` only count next to another reason or together. `File.piiOverride` is the owner's choice (`PATCH /api/files/[id]` with `sensitive`); `DetectPII` never changes a file that has one, and `null` hands it back to the model.
- Search index: write file entries with `upsertFileSearchEntry(fileId)` (`server/utils/search.ts`), which re-reads the row and serializes writes, never with Orama `insert`/`update` directly. Orama only holds text; vectors live in `server/utils/vectorIndex.ts` and only those made by the active preset's models are loaded (`reloadFileVectors`). `search:refresh` indexes files analyzed by the other blue/green color. Every Orama index uses `createSearchTokenizer` (`server/utils/orama.ts`) instead of Orama's English splitter, which drops non-Latin letters: it splits on Unicode letters and numbers, lowercases and folds diacritics (`İ`, `ı`, `ş`, `ё`, Greek tonos, Arabic harakat), stems only `a-z` words with the English stemmer, splits Han and kana into bigrams (documents also get the last character, so single characters still match by prefix) and Thai, Lao, Khmer and Myanmar into words with `Intl.Segmenter`. The smart-mode whole-word filter tokenizes with the same tokenizer (`fileSearchDb.tokenizer`). `searchFileIds` runs fulltext only for visitors, when AI is off for the instance or the user, or in fulltext mode; smart mode fuses the image, text and whole-word fulltext lists, each cut by its model's calibrated floor and ratio, and falls back to fulltext while a query model is still loading.
- PWA (`ENABLE_PWA`, build time): `@vite-pwa/nuxt` writes `/manifest.json` from `pwa.manifest` in `nuxt.config.ts` and a Workbox `sw.js` with `navigateFallback: null` (pages are server rendered, so there is no app shell to fall back to). With `ENABLE_PWA=false` neither exists and the head has no manifest link. The manifest's `share_target` posts shared `files`, `title`, `text` and `url` as multipart to `/dashboard/share`. That POST comes from outside the app and the `Lax` session cookie cannot be relied on, so `public/share-target.js` (pulled into the worker through `workbox.importScripts`, versioned with the Fileship version) intercepts it, stores every file under `/dashboard/share/<id>/<n>` (name in `X-File-Name`) and the text (line breaks turned back into `\n`, multipart sends CRLF) under `/dashboard/share/<id>/text` in the `fileship-share` Cache Storage cache, drops entries older than a day and answers with a 303 to the page (`?failed=1` when storing failed). The page (`pages/(dashboard)/dashboard/share.vue`, `user-only`, so a logged-out user logs in and comes back to the same items) reads that cache, uploads the files with `useUploader().upload` (whose `results` are aligned with the files) and the `UploadOptions` fields the upload sheet uses, shortens links or saves them and text as notes, deletes each cache entry once it is saved or removed and lists the resulting links with copy buttons. iOS has no Web Share Target.
- `app/utils/socket.ts`: socket.io client that keeps user, theme, embed, domains, passkeys, lists and the storage usage in sync.
- Email: `sendEmail({ to, language, template, params, path })` (`server/utils/email.ts`) renders the `emails.<template>` messages in the recipient's language (`emailLanguage(user, event)`: `User.language`, then the request's language, then English) as accessible HTML and plain text, and sends them with nodemailer through the instance's SMTP settings. Action links are built from the `siteUrl` setting, never from the request host. Email is optional: `isEmailConfigured(settings)` (public `emailEnabled`) needs `siteUrl`, `smtpHost` and `smtpFrom`, and every email feature hides itself without it. `POST /api/settings/email-test` sends a test with unsaved form values (stored password unless a new one is typed, which then needs `verifySession`).
- Email addresses: `User.email` is the confirmed address (unique, lowercase) and `User.pendingEmail` the one waiting for its `/verify-email?token=` link (`PUT`/`DELETE /api/users/@me/email`, both behind `verifySession`; `POST /api/auth/verify-email`). Only confirmed addresses receive account emails. `updateUserEmail` (`server/utils/emailToken.ts`) saves both and syncs them over `currentUser:update` and `user:update`; the users page shows the address and whether it is confirmed.
- Storage usage: `GET /api/users/@me/storage` returns `{ used, limit }` in bytes as strings (`limit` is `null` for admins and `usableSpace` -1), computed with `usableSpaceOf` and `storageUsedBy` from `server/utils/upload.ts`, the same rule `exceedsUsableSpace` enforces (trashed files count). The client keeps it in `useStorageUsage()`, refreshed by `socket.ts` on file, trash and user events. `StorageMeter` draws it (bar when limited, `IInfinity` when not) in the sidebar, the users page and the stats page; quota sizes use `formatStorageSize` (base 2, because limits are entered in MB). Quota rejections carry `data.quotaExceeded`, and a counted view sends `file:update` with `views`.
- Duplicates: `File.contentHash` is the SHA-256 of the stored bytes, and only files that have the same size as another non-trashed file of their owner are hashed (`server/utils/duplicates.ts`). `hashFile` streams the bytes from the storage once per file (concurrent calls share the promise), `syncContentHashes` hashes every such file in the background (on startup through `files:hash`, after `indexCreatedFile` and after trash restores), and `GET /api/files/duplicates` groups the hashed files of the user by hash, most wasted space first, for the Duplicates card on the storage page. Before an upload, `useUploader` sends the sizes to `POST /api/files/duplicates`; files that have a same-size match are hashed with Web Crypto (secure contexts, up to 256 MB) and checked again, and a match asks **Upload anyway** or **Skip duplicates**. Images the server re-encodes (`isProcessableImage`: EXIF removal and compression change their bytes) and files the browser could not hash are uploaded with `reportDuplicate`, and the server sends `file:duplicate` once the stored file has been compared.
- Storage warnings (`server/utils/storageWarning.ts`): a user with a limit and a confirmed address gets one email when `storageUsedBy` passes 90% of `usableSpaceOf`. `indexCreatedFile` queues a check (debounced per user, with the uploader's language as a hint), and the `email:storageWarnings` sweep (every 10 minutes) catches deletes and lowered limits. `User.storageWarnedAt` remembers the warning, is claimed atomically (so both colors send once), is cleared when usage drops below 90% and again when sending fails.

## Telemetry

- The report schema is `reportSchema` in `packages/telemetry/src/schema.ts`. The dashboard (`server/tasks/telemetry/collect.ts`) and the panel both validate against it, so change it in one place and keep older reports readable.
- Reports are anonymous: counts, sizes, on/off flags and version strings only. Never add names, file names, captions, URLs, domains, hosts, IP addresses or setting values such as keys. The instance id is the random `data/.fileship_project_id`.
- The dashboard collects nothing while telemetry is off. It sends one report five minutes after startup and then every six hours (`POST /api/v2/report`). Instances older than 6.0 still call `POST /api/event`, which the panel keeps accepting.

## Telemetry panel (`apps/telemetry`)

- Same structure and conventions as the dashboard, on the ui layer, with the default Fileship colors and a light/dark toggle.
- `Report` keeps one row per instance and UTC day (`@@unique([instanceId, day])`). Ingestion (`saveReport` in `server/utils/ingest.ts`) upserts that row; legacy events are merged into it and carry the instance's last known values forward. Ingestion is rate limited per instance and per client (at most 5 new instances per client a day) and never stores IP addresses.
- An instance is active on a day when it reported in the `ACTIVE_DAYS` (7) days up to and including it; a day's totals add up the latest report of every active instance (`computeDay` in `server/utils/rollup.ts`). `DailyStat` stores those totals. `stats:rollup` (hourly) fills missing days and recomputes only today and yesterday, so pages read ready rows and past days never change.
- `db:prune` (daily and on startup) runs the rollup first, then deletes instances silent for `NUXT_INSTANCE_RETENTION_DAYS` with their reports, reports older than 13 months and expired sessions. `DailyStat` is never pruned.
- Access is a single admin password (`NUXT_ADMIN_PASSWORD`), compared through scrypt with a per-process salt and `timingSafeEqual` (`isAdminPassword`; a plain hash of a password is flagged by CodeQL). Sessions are random tokens stored as SHA-256 hashes, sent in the httpOnly `telemetryToken` cookie and expiring after 30 days. Failed logins are rate limited per IP and across all addresses, and cookie-authenticated writes reject cross-site requests like the dashboard.

## Desktop app (`apps/desktop`)

- **Processes:** Fileship for Windows needs 64-bit Windows 11 24H2 (build 26100) or newer: the installer (`customInit` in `build/installer.nsh`, also on silent updates) and the host (`isSupportedWindows` in `native/host/main.cpp`, for copies that skip the installer) refuse anything older.
    - `fileship-host.exe` (`native/host`, C++20 / C++/WinRT) is the app. It starts with Windows (`--hidden`), owns the tray, hotkeys, notifications, capture, the overlay, recording, uploads, history, the store, the updater and Harbor's Fileship side, and idles at a few MB of private memory. `scripts/host.mjs` builds it with MSVC (shared setup in `scripts/msvc.mjs`, one object folder per source folder, cleared before each build) from `native/shared`, `native/core`, `native/ui` and `native/host` into `build/host`, which ships as `resources/host`. It counts as packaged only inside `resources\host` next to `Fileship.exe`; anywhere else it never touches the shell verbs or the startup entry.
    - `native/shared`: WinHTTP client (`http.h`, also used by the Harbor helper), socket.io v5 client over WinHTTP WebSocket (`socketio.h`; it reconnects with backoff, up to 5 s after a dropped connection and about a minute after the server closed or refused it, calls `onReconnect` after any earlier attempt and reports `connect_error` through `onConnectError`), JSON on `Windows.Data.Json`, the log and `t()` (`i18n.h`, the same rules as the renderer's catalogs). `native/core`: screen capture (GDI, or DXGI Desktop Duplication per output while a fullscreen app is shown, because GDI returns stale frames of fullscreen games), window and DXGI output enumeration, WIC encoding and sounds.
    - `scripts/native-assets.mjs` generates `build/generated/theme.h` (the ui layer's light and dark tokens from `tailwind.css`, converted from OKLCH), `build/generated/icons.h` (the lucide icons the native UI draws), the merged catalogs in `build/host/i18n` and the Geist font files in `build/host/fonts`; `scripts/host-settings.mjs` writes the settings defaults and schema from `shared/settings.ts`.
    - Electron (`electron/`) only runs while a window is open: the main window, the login window and the dashboard window. The host starts it (`--host-pipe <name>` plus `--route <route>` or `--dashboard <route>`) or sends `window:show` / `window:dashboard` when it is connected; Electron starts the host when it is not running, quits a minute after its last window closes and when the host goes away. tsdown bundles it into `dist-electron/main.cjs` and `preload.cjs`; keep runtime packages in `devDependencies`.
    - `app/` is a Nuxt SPA on the ui layer, served from the `app://fileship` protocol (`electron/protocol.ts`).
- **IPC:** the renderer talks to Electron through the typed bridge in `shared/ipc.ts` (`window.fileship`, `desktop(channel, ...args)`). Electron handles `LOCAL_CHANNELS` (login, logout, dashboard, theme, file dialogs) and forwards every other channel unchanged to the host over the named pipe `\\.\pipe\fileship-host-<SID>` (`--pipe` overrides it), as newline-delimited JSON: `{id, channel, args}` → `{id, ok, result}` or `{id, ok: false, error, data}`, and events `{event, payload}` (`HostInvoke`, `HostEvents`). The host registers handlers with `registerHandler` (`native/host/rpc.h`) and the pipe only accepts the current user. Add every channel to the types and the channel lists. Handlers in `electron/ipc.ts` reject senders that are not app pages. A second host instance forwards `--upload`, `--harbor-action` and `--show` to the running one.
- **Login:** the instance's own `/login` runs in a temporary Electron partition. Its httpOnly `token` cookie is handed to the host (`account:setSession`), which checks the user and stores the session DPAPI protected; existing Electron `safeStorage` values (`v10`, key from `Local State`) are migrated once. The user agent carries `FileshipDesktop/<version>`, so the session shows as "Fileship for Windows". Single sign-on works in that window too, because the provider redirects back to the instance, which sets the same cookie. The app requires Fileship `MIN_FILESHIP_VERSION` (6.0.0) from `/api/healthz`.
- **Dashboard:** file management is not rebuilt in the app. The Dashboard window loads the instance itself, in the `persist:dashboard` partition with the session cookie (`account:token`). Other origins and pop-ups open in the browser, with two exceptions for single sign-on (`keepOnInstance` in `electron/dashboard.ts`): a main-frame navigation or redirect to an authorization URL whose `redirect_uri` is the instance's `/api/auth/oidc/callback` starts a chain whose pages stay in the window until it is back on the instance (linking), and `window.open` of `/api/auth/oidc/verify` opens a child window in the same partition, so `/sso` reaches the dashboard over the `fileship-sso` BroadcastChannel; that pop-up follows the same rule and opens no windows of its own. Because the session is shared, logging out there logs the app out too: when the window lands on `/login` Electron asks the host to re-check the account, which runs `handleUnauthorized` on 401, and `account:changed` with `null` closes the window; Harbor's socket handles the server's `logout` event.
- **Updates:** the host reads `latest.yml` from the public `hanzydev/fileship-desktop` releases (`native/host/updater.cpp`), downloads the installer, checks its `sha512`, and runs it with `/S --updated --force-run` on restart or quit, never while uploads, recordings, an open overlay or a task are running. It checks 10 s after start and every 4 hours (15 minutes after a failure), and only one check runs at a time (claimed under the updater lock). `.github/workflows/desktop-release.yml` builds and publishes on `desktop-v*` tags (it creates the release as a draft first, because electron-builder races two publishers when it has to create the release itself, and publishes it after the upload) (`DESKTOP_RELEASE_TOKEN` secret). `build/installer.nsh` stops the host, the Harbor helper and Electron before an install.
- **Capture:** global hotkeys (`native/host/hotkeys.cpp`, `RegisterHotKey`, Electron accelerator strings, ShareX-like defaults with Print Screen on the active monitor) and the tray run actions from `native/host/actions.cpp`. Region capture opens one native overlay window over the whole virtual screen (`native/ui/overlay.cpp`, Direct2D on a DirectComposition swap chain), created per capture and destroyed after it, so selections and annotations can span monitors. Releasing the mouse finishes every purpose right away: a drag takes the dragged rect and a plain click takes the window (or control) under the cursor, or its monitor when it is on the desktop. Annotations can be drawn anywhere before the region is picked: with no tool selected (region mode, `C`) a drag picks the region, a click picks the window and shapes can still be selected and moved; Escape closes an open popover, then deselects the shape; right-click deselects, then returns to region mode. Space, Enter and 1-9 finish with the whole screen, the hovered target or a monitor, cut from the frozen snapshot, so the annotations are kept. The single toolbar starts at the top centre of the primary display and can be dragged onto any monitor; its placement (`{ display, edge, cx, cy }`) and the per-tool colours and sizes are stored in the host store (`overlay`), and every display draws at its own DPI. The overlay gets one BGRA snapshot per display (uploaded to the GPU, then freed) and the window rects, all in physical virtual-screen coordinates, and every callback runs on the UI thread of `native/ui` (`uiThread.cpp`). Once the pixels are taken the host plays `shutter.wav` unless `capture.playSound` is off; it also plays when a text capture region is picked and when a recording finishes. Explicit uploads (file, clipboard, drag and drop) always upload and skip the after-capture settings, and a screenshot whose upload fails is saved to the save folder like a recording, so a capture is never lost. A screenshot counts as saved only when it was written; with uploads off, one that could not be saved is copied to the clipboard. A rejection with `data.quotaExceeded` notifies that the storage is full and opens the dashboard's storage page on click, and Harbor does not retry it. Uploads finish with `uploaded.wav` unless `afterUpload.playSound` is off (Harbor uploads stay silent); `scripts/sounds.mjs` derives it from the shutter sound. Results go through `native/host/tasks.cpp` for the after-capture and after-upload tasks, uploads are chunked through `native/host/upload.cpp`, which sends up to the server's `uploadConcurrency` chunks at once and reports progress to the app (Electron turns it into taskbar progress) and the tray tooltip, and every item lands in the SQLite history (`history.cpp`, Windows' `winsqlite3`, the same `history.db`). Text capture opens the overlay with the `ocr` purpose, which has no annotations, sends the region as PNG to `POST /api/ai/ocr` and copies the text; the endpoint runs the instance's OCR model without storing anything, needs AI on for the instance and the user, and is rate limited per user. `native/ui/demo` (`scripts/overlay-demo.mjs`) opens the overlay on a synthetic snapshot and renders fixtures to PNG, so the overlay can be tested without capturing the real screen.
- **Annotations:** `native/ui/annotator.cpp` holds the shapes as plain data with undo/redo (100 steps) and draws them with Direct2D above the snapshot; blur (the same stack blur as Konva) and pixelate read that snapshot. The toolbar and its popovers (`toolbar.cpp`, `widgets.cpp`) are drawn to match the shadcn-vue components (sizes, radii and theme tokens from `theme.h`, Geist through DirectWrite, lucide icons from `icons.h`). There is no separate editor window on purpose: annotating happens only while picking a region.
- **Recording:** `native/host/recording/`. ffmpeg is the pinned gyan.dev build that `ffmpeg.cpp` downloads to `userData/ffmpeg` (SHA-256 checked) or a custom path; encoders are probed once per binary (`ffmpegProbe` in the store). Video comes from `ddagrab` on the DXGI adapter and output that hold the area, or `gdigrab` for areas that span monitors. Audio is captured with WASAPI (`audio.cpp`): the microphone (`recording:microphones` lists the endpoints; `audio.microphoneId` holds an endpoint id, and an unknown or empty id uses the default device) opens in the communications category when noise suppression, echo cancellation or gain control is on, so Windows 11 applies its voice processing, and system audio is a loopback of the default output; both are converted to 48 kHz float stereo, mixed or split into tracks and streamed as f32le PCM through one named pipe per track. Each pipe is primed with silence, and audio starts at the sample of the first video frame (`showinfo`). After `q` the pipes are closed, or ffmpeg waits on them forever. Pausing ends the segment; segments are joined with the concat demuxer, and GIFs are recorded losslessly and converted with a palette pass. The area is outlined by native border windows (`native/ui/recorderUi.cpp`, off with `recording.showBorder`), and the native toolbar sits on the display that holds the largest part; both are excluded from capture (`WDA_EXCLUDEFROMCAPTURE`).
- **Fileship Harbor** ("Harbor"): the user's files and folders in File Explorer through the Windows Cloud Files API. Code, settings, file names and i18n keys all say `harbor`.
    - `native/harbor/` is a C++20 / C++/WinRT helper (`fileship-harbor.exe`) built with MSVC by `scripts/harbor.mjs` into `build/harbor`; it needs Visual Studio Build Tools with the x64 C++ toolset and ships as `resources/harbor`.
    - It registers the sync root (`Fileship!<SID>!<account key>`, always-full population), creates placeholders with identities `f:<fileId>` / `d:<folderId>`, hydrates them itself with WinHTTP range requests to `/u/<id>`, asks before renames and moves (including moves to the Recycle Bin, which leave the sync root), reports completed deletes (`NOTIFY_DELETE_COMPLETION`, skipped when the same placeholder is still there, because the shell probes with a delete before recycling), and watches for new and edited files. Before a Harbor upload the file is turned into a not-in-sync placeholder (`prepare`, new files get a temporary `p:` identity), its progress goes to Explorer's Status column with `CfReportProviderProgress` (`progress`), and `adopt` sets the real identity and marks it in sync. An edit is a placeholder whose last write time differs from its creation time. Uploads send a `stamp` (size and last write time) taken before the file was read; a file that changed during its upload is adopted without resetting that baseline and the watcher `recheck`s it, so the newer content is uploaded again. Adopting a folder returns its direct children that still need syncing. Only `ERROR_NOT_A_CLOUD_FILE` on an item without a cloud reparse tag means "not a placeholder" (`probeIdentity`); any other failure to read an identity is unknown, so the watcher tries the item again later and `scan` marks it `unreadable` instead of reporting it as new. `scan` lists every folder on its own: a folder it cannot list is reported `unreadable` and the scan goes on, and only an unreadable Harbor folder fails it. `remove` (items deleted on Fileship) deletes only in-sync, unmodified placeholders, never recursively; a folder that keeps anything is reverted to an ordinary folder (`CfRevertPlaceholder`) and its contents are reported back.
    - `native/host/harbor/` owns the Fileship side and talks to the helper over stdio JSON lines (`helper.cpp`): it loads folders and files, maps names to safe, unique Windows paths (`paths.cpp`), applies socket events, and turns Explorer actions into API calls (every delete, Recycle Bin or Shift + Delete, → trash, never a permanent delete; deleting a short link deletes it, rename and move → `PATCH`, new file → upload, edited file → upload as a new file into the folder it is in locally and trash the old one). Deletes are batched until Explorer has been quiet for 3 s, and items inside a folder deleted in the same batch are skipped, so a tree goes to the trash with one `deletedAt`. Socket events are applied incrementally: partial `file:update` payloads (view counts, AI results) are merged into the known file, `link:update` click counts (no `code`) are ignored, and `folder:delete` drops the subtree and moves its remaining files to the parent; only `trash:restore`, `currentUser:update`, `deleteAll`, reconnects and rescans reload everything, and reloads are coalesced so at most one waits. A refused socket makes Harbor check `GET /api/users/@me` (a 401 logs out). Folder names are at most 32 characters: longer renames are refused, and a new local folder is shortened before it is created. A kept folder or file that `remove` left behind is created or uploaded again. Folders nest like on Fileship: each folder is placed under its parent, a folder made, renamed or moved inside another is created or moved there (`parentId`), and moving anything into a folder that is not a Fileship folder (Notes, Links) is refused. Harbor shows only the user's own folders and files: socket events for items another user owns (shared folders) are ignored. A file whose placeholder was replaced instead of written in place (editors that save atomically) arrives as `localNew` on the path of a known identity and is treated as an edit of it. Before `localNew` creates anything on the server, the engine reads the path's identity again (helper `identity`, which also says whether the path still `exists`) and only records a placeholder it finds; a read that fails is retried, never treated as new, and a path that is gone is skipped. A server item whose `adopt` fails right after Harbor created it is deleted for good. A new item whose folder is not on Fileship yet is retried 5 times. `stopHarbor` blocks until the helper has stopped, so never call it on the host's message loop.
    - Notes and short links live in two virtual root folders (`v:notes`, `v:links`, named in the app language, shown only with the matching permission; a Fileship folder with the same name keeps it). Notes are `n:<id>` `.md` files: saving one `PATCH`es the note, renaming changes its title, a new `.md` or `.txt` creates a note, and a remote change updates the placeholder with `refresh` (new size, dehydrated, re-pinned) unless it was edited locally. A reload refreshes note placeholders whose size no longer matches the note, and a download whose content length still does not match fails and the helper sends `noteChanged`; the host loads the note again and refreshes the placeholder. Links are read-only `l:<code>` `.url` files that the helper generates itself; deleting one deletes the short link. Virtual folders cannot be renamed, moved or recycled, and nothing moves in or out of them.
    - Pausing (`pauseHarbor`, in memory) ignores `localNew`/`localModified` and skips applying remote changes; deletes and renames still sync because Explorer waits for them, and resuming resyncs, and its scan uploads what waited. `freeUpSpace` dehydrates in-sync, unpinned `f:`/`n:` files. The last 50 operations are kept for the settings page (`harbor:activity`).
    - Explorer integration: the helper hosts COM classes in its MTA (`com.cpp`: one `shellClasses()` entry each, a `ServerLock` member, the GUID also in `installer.nsh`): `ThumbnailProvider`, `ShareHandler` (copies the link) and `StorageProviderStatusUISourceFactory` (the Windows 11 flyout). The flyout (`status.cpp`) renders the JSON the host sends with `syncStatus` (`state`, a localized `message` with an `action`, and `quota` with its label; `total` 0 means unlimited and becomes `UINT64_MAX`), plus the sync status command and the Open Fileship, Upload, Pause/Resume, Trash and Settings buttons (`ACTIONS`); every `GetStatusUI` sends `statusRequested`, and the host refreshes the storage and the on-device size (`usage`) at most every 10 s, so Explorer always shows fresh data. With Fileship closed, COM starts `-Embedding`, which reads `%LOCALAPPDATA%\Fileship\harbor.json` and launches the host with `--harbor-action` when needed. Custom states (password, expiry, sensitive, views; names translated at `init`) are sent with `setStates` when they change, and every state carries an icon (`iconOf` in `states.cpp`): Explorer crashes on a state without one. `native/host/shell.cpp` writes the `FileshipHarbor*` verbs (copy link, open in browser, show in the dashboard, and on folders copy the folder or inbox link) with `AppliesTo` limited to the Harbor folder, hides "Upload to Fileship" there and removes them when Harbor is turned off. New placeholders in a pinned folder are pinned and hydrated. The watcher hands pin changes (hydrate pinned, dehydrate unpinned files) to up to four background threads, one job per file, which read the pin state again when they start.
    - Harbor only uses an empty folder: choosing a non-empty one is refused, and a start in a non-empty folder that holds no Fileship placeholders is undone (`harborRoot` in the store remembers the folder Harbor owns; logging out forgets it).
    - Logging out or turning Harbor off removes only placeholders that are in sync (scanned first), nested folders before their parents, so edits that were not uploaded, pending uploads and ordinary files stay on disk; then it unregisters the sync root, unless the scan failed or reported an unreadable item (a warning is logged and the root stays registered, so the online-only placeholders left on disk still open when Harbor starts there again). The uninstaller runs `--unregister-all` except during updates.
- **Windows:** the Electron main window exists only while it is open, and Electron itself quits a minute after its last window closes; the host keeps running in the tray. A `--hidden` start creates no window. The host starts with Windows (the `Fileship` value of the Run key, `--hidden`) and keeps a single instance (`Local\FileshipHost`).

## Browser extension (`apps/extension`)

- **Tooling:** [WXT](https://wxt.dev) builds Manifest V3 for Chrome/Edge and Firefox from one codebase (`wxt.config.ts`, `manifestVersion: 3`; WXT would build Firefox as MV2 otherwise). Entrypoints live in `entrypoints/`, and WXT auto-imports `utils/` and `composables/` like Nuxt. Nuxt is not used; Vue comes through `@wxt-dev/module-vue`.
- **Design system:** the pages reuse the ui layer without Nuxt: the `#layers/ui` alias points at `packages/ui`, `cn` is an auto-import, the stylesheet imports the layer's `tailwind.css`, and unplugin-vue-components registers the layer's components with Nuxt names (`UiButton`, `UiCardHeader`, `EmptyState`, `TextBlock`, `PasswordInput`) and lucide icons as `<IName />`. The layer's other app components need Nuxt and are excluded in `globsExclude`; add one to `UI_APP_COMPONENTS` only if it works without Nuxt. Pages follow the system theme by toggling `.dark` (`mountApp` in `utils/app.ts`), and Geist comes from `@fontsource-variable/geist`.
- **Entrypoints:** `background.ts` (context menus, messages, notifications, and every upload and short link), `popup` (toolbar), `options` (connection and upload options), `upload` (a tab with a drop zone; the Firefox popup opens it because Firefox closes popups when a file picker opens), `offscreen` (Chrome only: copies to the clipboard with `execCommand`, since a service worker cannot; Firefox writes the clipboard from its background page) and `area.ts` (the area picker, injected on demand with `scripting.executeScript`).
- **Connection:** `local:settings` (`utils/settings.ts`) holds the instance URL, the upload token, the last connection test (`connection`: site name, version, `canUpload`, `canShorten`) and the upload options (`fileNameType`, `expiration`). The token never leaves `storage.local` except as `Authorization: Bearer` to the instance, and is never logged. Requests use `credentials: 'omit'`. `testConnection` (`utils/api.ts`) reads `/api/healthz` (6.0.0 or newer) and probes `POST /api/files` with an empty form and `POST /api/links` with `{}`: 401 is an invalid token, 403 a missing permission, anything else means allowed, and nothing is created.
- **Permissions:** no host permission at install. The options page requests the instance origin (`optional_host_permissions`) inside the click handler, before any `await`, and removes the old origin when the address changes or on **Disconnect**. Images from another origin than their page request that origin from the context menu click (synchronously, in the same handler); same-origin and `blob:` images are fetched inside the page with `activeTab` + `scripting`. `activeTab` also covers `captureVisibleTab` and the area picker, so the popup and the menus are the only ways in.
- **Uploads:** `uploadBlob` (`utils/upload.ts`) mirrors the desktop client: chunk size and parallel requests come from `/api/settings/public` (cached 5 minutes per instance), chunks carry `uploadId`, `currentChunk`, `totalChunks`, `chunkOffset`, `fileNameType` and `expiration`, and 0/5xx responses are retried up to three times. Errors become translated text in `describeError` (`utils/errors.ts`): `data.quotaExceeded`, 401, 403, timeouts and `ExtensionError` keys.
- **Tasks:** the background runs everything through `runTask`, which keeps the list in `session:tasks` (the popup and the upload page watch it with `useTasks`), copies the link, shows a notification (clicking it opens the link) and calls an extension API every 20 seconds so Chrome keeps the service worker alive during long uploads. Tasks still running when the worker starts again are marked as interrupted. Files picked in the popup are handed to the background through IndexedDB (`utils/files.ts`), because extension messages cannot carry `File` objects in Chrome; the record is removed only after its upload, because Firefox cannot read a stored file once its record is deleted.
- **Area picker:** a closed shadow root over the page, styled with inline styles (page CSP cannot block them); a drag selects, a click takes the visible page, Esc or a right click cancels. It removes itself and waits two frames before sending `areaSelected`, and the background crops the `captureVisibleTab` image by `image width / innerWidth`, which covers device pixel ratio and zoom.
- **Packages:** `pnpm --filter extension package` writes `fileship-<version>-chrome.zip`, `-firefox.zip` and `-sources.zip` to `.output`. The sources zip is taken from the repository root (`zip.sourcesRoot`) with only the extension (without `apps/extension/store`), `packages/ui`, `packages/eslint-config`, the root manifests, the root `.gitignore` and `docs/browser-extension.md`, and rebuilding it gives exactly the files of the Firefox zip (steps in `docs/browser-extension.md`). The Firefox manifest has the gecko id `fileship@hanzy.dev`, `strict_min_version` 142 and declares `websiteContent` and `browsingActivity` as data it sends; the Chrome manifest sets `minimum_chrome_version` 116 and leaves out `_locales/az`, a locale Chrome does not support (`CHROME_UNSUPPORTED_LOCALES`). The store listing texts, the privacy form answers and the reviewer notes are in `apps/extension/store/listing.md`, the store images in `apps/extension/store/images`, and the privacy policy is `docs/browser-extension-privacy.md`. An `extension-v<version>` tag runs `.github/workflows/extension-release.yml`, which packages the extension, rebuilds the Firefox zip from the sources zip and fails if they differ, and submits the Chrome zip to the Chrome Web Store (API v2, service account) and the Firefox and sources zips to addons.mozilla.org (API v5, JWT) with `wxt submit`; the steps and secrets are in MEMORY.md under Releasing. `assets/tailwind.css` leaves `store` out of Tailwind's sources, because the sources zip does not carry it.

## Conventions

- Code style: no comments, `handle*` names for event handlers, `<template>` before `<script setup>`, `definePageMeta` last, non-null `!` and `as any` are fine where the type is known.
- Prettier: 4 spaces, single quotes, semicolons, trailing commas, width 100. Format only the files you changed.
- Create a component only when it is used in more than one place.
- Errors: `createError({ status, statusText?, message, data? })`. `statusCode` and `statusMessage` are deprecated.
- Long lists use virtual scroll with `reachEnd`, never pagination controls.
- Commits: conventional commits (`feat`, `fix(ui)`, `fix(api)`, `chore`, `docs`, ...), one topic per commit.
- User documentation lives in `docs/` (installation, configuration, updating, upgrading, AI, the Windows app, the browser extension, telemetry). `README.md` stays short: what Fileship is, the demo GIF, the features in one line each, the comparison with other file hosts, a quick start and links into `docs/`. Put details in the matching `docs/` page, not in the README. The README is translated into the eleven other app languages (`README.<code>.md`: `tr`, `de`, `es`, `fr`, `it`, `pt-BR`, `ru`, `az`, `ja`, `ko`, `zh-CN`) with the same lines in the same order, a language switcher in the header and the UI labels the dashboard uses in that language; a change to `README.md` changes every translation in the same commit. `docs/` stays English only.

## UI rules

- Use shadcn-vue components. Read `https://www.shadcn-vue.com/docs/components/<name>` before using one and follow its documented composition.
- Never restyle `packages/ui/app/components/ui`. Small upstream logic or attribute fixes are acceptable; colors, radii and spacing are not changed there. Adjust at the usage site instead.

## Security notes

- `/u/[id]` serves user uploads with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`; HTML, SVG, XML and JavaScript are served as attachments. PDFs keep the same headers: `PdfViewer` fetches their bytes (the sandbox only applies to documents rendered from the response) and draws them with pdf.js, without scripting, XFA or an annotation layer, so the browser's own PDF viewer is never involved. `/u/[id]`, thumbnails and `GET /api/files/[id]` look a file up by id first, then by `fileName` (`fileLookups` in `server/utils/fileAccess.ts`). Visitors get 404 for trashed, expired and sensitive files (`isHiddenFromVisitors`) and never receive internal fields (`visitorFileFields`). A counted view is claimed once per IP, user agent and file per 10 minutes (`claimView`), and the view that reaches `maxViews` is still served; the file is deleted when that response closes.
- Orama indexes are shared; every search must filter by `authorId`.
- Shared folders: never decide access to a file or folder by `authorId === currentUser.id` alone; members of a shared tree reach it through `folderAccessOf` / `fileAccessOf`, and outsiders must keep getting 404 or 403.
- Public folders list password protected files to visitors only as `{ id, fileName, mimeType, size, createdAt, isLocked: true }` (their `name` is the `fileName`), matched by `fileName` only; their bytes need the password (`GET /api/files/[id]` is rate limited per IP and file). Sensitive files (`piiDetected`) are never shown to visitors, and folder archives leave out locked and sensitive files. Visitor queries use `visitorFileWhere(owner)`, which also hides images and text files that are not analyzed yet while AI is on.
- Backup restores accept an explicit allow-list of fields per model and always force the owner to the current user.
- Upload ids, file names and paths are validated before touching the filesystem.
- Sensitive account actions go through `verifySession` on the server and `withVerification` on the client.
- Single sign-on (`server/utils/oidc.ts`, `server/api/auth/oidc/*`, `/api/users/@me/oidc`) uses `openid-client` with the authorization code flow, PKCE (S256), `state` and `nonce`. The flow state lives in the httpOnly, `Lax`, 10-minute `oidcFlow` cookie (path `/api/auth/oidc`), AES-GCM encrypted with `<data>/secret.key` and read once by the callback, which checks `state` against it, so a callback URL cannot be replayed in another browser. The redirect URI is always built from the `siteUrl` setting, never from the request; a login started at another host is redirected to `siteUrl` once (`hop=1`), while linking and verification refuse other hosts. Discovery is cached for an hour per issuer, client and secret; `http:` issuers are allowed for local providers. `isOidcConfigured(settings)` needs `oidcEnabled`, `siteUrl`, the issuer and the client ID. The callback finds the account by its `OidcIdentity` (`@@unique([issuer, subject])`, one per user and issuer), then by a confirmed `User.email` equal to the provider's email when `email_verified` is true (refused when that user already has another identity of the issuer), then creates one when `oidcAutoRegister` is on (registration permissions and usable space, no password: `User.password` is nullable). Linking (`POST /api/users/@me/oidc`) and unlinking (`DELETE`) go through `verifySession`; unlinking is refused while the user has neither a password nor a passkey, or cannot log in with them (`canLogInWithPassword`). `verifySession` offers `oidc` as a method to linked users: the dashboard opens `/api/auth/oidc/verify` in a pop-up (`max_age=0`), the callback sets `Session.lastVerify` when the provider account is the linked one, and `/sso` reports the result over the `fileship-sso` BroadcastChannel. `passwordLoginEnabled: false` makes password and passkey logins answer 403 for everyone except super admins, only while single sign-on is configured (`isPasswordLoginEnabled`). Provider logins skip TOTP, and every callback, start and test is rate limited.
- Sessions are random tokens stored as SHA-256 hashes (`Session.tokenHash`). Browsers send them only in the httpOnly `token` cookie and the web client never reads or writes auth cookies. Native clients such as the desktop app send the same token as `Authorization: Bearer`, which works on every route and on the socket, and skips the cross-site check because browsers never send it on their own. Sessions have no expiry and end only when they are revoked. Impersonation runs on the server (`/api/auth/impersonate`), with the admin's token kept in the httpOnly `adminToken` cookie.
- Email tokens (`EmailToken`: confirmation and password reset links) are random 32-byte values stored as SHA-256 hashes, expire, are single use (`consumeEmailToken` deletes the row before acting) and replace older tokens of the same type; `db:deleteExpired` removes expired ones. Confirming a new address deletes every other token of the user.
- Invites: admins invite an address from the users page (`POST /api/invites`, Admin permission needs `verifySession`, rate limited per admin). `Invite` keeps the hashed token, the permissions and the usable space for 7 days; inviting the same address again replaces it and `db:deleteExpired` removes expired ones. `/register?invite=` reads it with `GET /api/auth/invite` and signs up through `POST /api/auth/register` with `invite`, which works while public registration is off, consumes the invite atomically, applies its permissions and limit, and stores the invited address as the confirmed `email` when no other account has it. Pending invites are refreshed over `invite:update`.
- Password reset (`/reset-password`, `POST /api/auth/password-reset`, `GET` and `POST …/confirm`): requests are rate limited per IP and per account name and always answer 204 (the token and email are made in `event.waitUntil`), so they never reveal whether an account exists. Only a confirmed address gets a link (1 hour, single use, refused once the address changes). Accounts with TOTP must also enter a code (5 tries per link), passkeys are left alone, nobody is logged in by a reset, and it ends every other session of the user.
- Storage configs are stored AES-GCM encrypted with the same `<data>/secret.key`. The API never returns secret fields; it sends `<field>: true/false` flags, and an empty secret on update keeps the stored value.
- Upload tokens (`fs_…`) are accepted only on `POST /api/files` and `POST /api/links`, through the `Authorization` header. They are stored hashed for lookup and AES-GCM encrypted for display, with the key in `<data>/secret.key`.
- Client IPs come from `getClientIp(event)` (`server/utils/clientIp.ts`), never `getRequestIP` with `xForwardedFor`: it trusts `X-Fileship-Client-IP` (set by Caddy from `{client_ip}` with `trusted_proxies_strict`) or the last `X-Forwarded-For` entry only when the peer is a private address or an internal hop, and otherwise uses the socket address.
- Login, passkey login, registration and step-up verification are rate limited (`rateLimit`). TOTP codes cannot be reused (`verifyTotpToken`). Cookie-authenticated writes are rejected when the browser marks them as cross-site (`Sec-Fetch-Site` other than `same-origin` or `none`). The check does not depend on the `Host` header, so it works behind any reverse proxy.
- Short links only accept `http` and `https` targets. Password protected links redirect to `/link/[code]`, and `POST /api/links/unlock` is rate limited.
- Webhook URLs and signing secrets are stored AES-GCM encrypted with `<data>/secret.key` and never returned: the API sends `host` and `hasSecret`, and an empty URL or secret on update keeps the stored value. Webhooks only reach public addresses (checked when saving and again for every request and redirect) unless a super admin turns on `webhookPrivateTargets`. **Send test** is rate limited per user.
- Markdown is rendered without raw HTML, and links are limited to `http`, `https`, `mailto` and relative URLs.
